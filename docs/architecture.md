# 架构与模块边界

## 项目定位

本项目是独立维护的 Agent 框架，第一条接入链路为 QQ（SnowLuma）→ 自有框架 → DeepSeek，网页任务使用 ego-lite。

框架采用单仓库和一个主要常驻进程，内部模块化。浏览器本身及其命令调用可以是外部进程；当前不额外引入微服务编排。

## 环境前置条件

Python 统一使用 Conda 环境 `Deepseek_bot`，版本基线为 3.12.x。每个里程碑先调研并验证对应环境，之后才进入实现或真实联调。具体规则见 [环境约定](development-environment.md)，本机状态见 [环境调查记录](environment-audit.md)。

## 依赖方向

1. 自有内核使用本项目定义的事件、会话、模型结果和工具结果格式。
2. 适配器负责外部协议到内部格式的转换。
3. 原生插件通过 `companion.api` 使用能力。
4. AstrBot 插件通过兼容导入入口和语义转换层调用原生能力。
5. 自有内核不导入 AstrBot 插件类型；兼容层依赖原生接口，依赖方向不反转。

## 模块职责

| 位置 | 职责 | 边界 |
| --- | --- | --- |
| `core/lifecycle` | 启停和资源清理 | 管理组件，不处理聊天策略 |
| `core/events` | 内部事件与消息模型 | 不保存平台专有原始结构作为通用格式 |
| `core/pipeline` | 编排消息处理阶段与扩展挂钩 | 不实现平台连接和数据库访问 |
| `core/agent` | 模型与工具调用循环 | 不直接控制 QQ 客户端或浏览器 |
| `core/sessions` | 会话标识、上下文与执行并发 | 不决定具体人格和主动交流策略 |
| `core/tools` | 工具登记、参数检查、执行与结果返回 | 与插件加载机制分开 |
| `core/permissions` | 根据身份、来源和能力检查执行范围 | 同进程插件不因此获得安全隔离 |
| `adapters` | OneBot、DeepSeek、ego-lite 接入 | 外部协议细节集中在这里 |
| `plugin_system` | 插件加载、配置、资源与生命周期 | 不把业务能力全部写进宿主 |
| `compat/astrbot` | 映射 AstrBot 接口和行为 | 只承诺兼容清单列出的能力 |
| `memory` | 记忆记录、范围与检索服务 | 具体提取和更新策略以后确定 |
| `persistence` | 数据库连接、存储实现与迁移 | 不直接决定记忆可见范围 |
| `management` | 状态、配置和管理操作接口 | 前端形式尚未确定 |
| `telemetry` | 日志、错误与用量 | 默认避免记录密钥和完整私人内容 |

已实现（M1–M3）：`core/lifecycle`（runner 与 worker 池）、`core/events`（InboundMessage + SessionKey）、`core/pipeline`（筛选链、记忆命令、固定应答）、`core/agent`（DeepSeek 有界上下文应答）、`core/sessions`（会话管理/去重/消息与用量存储）、`core/permissions`（角色/能力/运行上下文）、`adapters/onebot`、`adapters/deepseek`、`memory`（显式记忆服务）、`persistence`（SQLite + 迁移 v1/v2）。其余目录仍为规划占位。

## 规划中的主流程

```text
SnowLuma 事件
  → 转成内部消息
  → 定位会话并检查来源
  → 插件处理阶段
  → 上下文准备与记忆检索挂钩
  → 模型／工具执行循环
  → 输出处理与发送
  → 保存记录与后续挂钩
```

这是目标流程，当前尚无执行实现。AstrBot 插件处理顺序、返回值和异步行为需要逐项确认，不能只映射同名函数。

## 执行与运行约定

- 同一会话的执行先按顺序组织；不同会话的并发由内核管理。
- 工具任务带有来源会话、发起身份和执行标识，便于检查范围、取消和追踪。
- 插件停用时清理它注册的处理器、工具和任务。
- 暂停、取消、超时、失败和完成需要有清楚的状态，具体状态结构在实现前定义。
- 框架版本、原生插件 API 版本和 AstrBot 兼容基线分别记录。

## 初始实现范围

先实现一条可验证的接入链路，并逐步扩展插件兼容范围。当前不创建额外平台、插件市场或具体自主活动策略的空实现。
